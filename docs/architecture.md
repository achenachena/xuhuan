# Xuhuan architecture

## Purpose

Xuhuan is a single-player, turn-based Telegram Mini App. The browser is responsible for presentation and animation; the API is responsible for identity, battle state, randomness, progression, and rewards. PostgreSQL is the system of record.

## Target system

```text
Telegram WebView
  │ raw initData in X-Telegram-Init-Data
  ▼
Next.js 16 Mini App on Vercel
  │ HTTPS JSON REST (OpenAPI 3.1)
  ▼
Go API on an arm64 Lambda Function URL
  ├── Neon PostgreSQL: players, catalog, battles, ledger, idempotency
  ├── Upstash Redis: distributed rate limits only
  ├── CloudWatch: short-retention logs and infrastructure alarms
  └── SQS/EventBridge: deferred until a concrete asynchronous feature exists
```

Vercel Blob continues to serve the existing character images. Cognito is intentionally absent from player authentication and is reserved for a future administrative UI. No service-to-service split, Kubernetes, WebSockets, or asset migration is justified for the current game.

## Trust boundaries and request flow

1. Telegram signs the raw Mini App `initData` payload.
2. The Mini App forwards that opaque value in `X-Telegram-Init-Data`. It never reads `initDataUnsafe` as proof of identity.
3. The Go API recomputes the Telegram HMAC, compares signatures in constant time, checks `auth_date` against `TELEGRAM_AUTH_MAX_AGE`, and parses the user ID as a signed 64-bit integer.
4. The API creates or refreshes the local player record and attaches the internal player UUID to the request context.
5. Public catalog reads return explicit DTOs. Player and battle endpoints always scope database work to the authenticated player.
6. A battle action locks the battle row and performs version and idempotency checks inside one PostgreSQL transaction. The API advances the deterministic state, records the action snapshot, and, on completion, updates the battle, ledger, and player together.
7. The Mini App animates the returned authoritative action result. It never calculates an outcome or submits a reward.

For local development, `X-Dev-Auth` is accepted only when all of these are true: `APP_ENV=development`, `DEV_AUTH_ENABLED=true`, and the header matches `DEV_AUTH_TOKEN`. Production configuration rejects development auth even if the other variables are accidentally set.

## Runtime components

### Mini App

- Next.js 16 App Router, React 19, TypeScript, Tailwind CSS, and SWR provide the presentation layer.
- Existing character selection, battle layout, animation timing, Chinese localization, Telegram theme integration, and audio providers are preserved.
- One API client owns base URL resolution, Telegram/development headers, error decoding, idempotency keys, and generated OpenAPI types.
- A `409 version_conflict` response causes the client to fetch the current battle before enabling another action.

### Go API

The API remains a modular monolith:

```text
apps/api/
  cmd/api/                 local HTTP process lifecycle
  cmd/lambda/              Function URL and release-operation entry point
  internal/application/    shared dependency construction and cleanup
  internal/lambdahttp/     Function URL to net/http adapter
  internal/api/            router, middleware, transport DTOs
  internal/auth/           Telegram and development authentication
  internal/battle/         deterministic rules and orchestration
  internal/character/      catalog domain
  internal/player/         player domain
  internal/repository/     repository interfaces and transactions
  internal/postgres/       pgx implementations
  internal/platform/       configuration, logging, telemetry
  migrations/              versioned SQL
  openapi/                 OpenAPI contract
  seed/                    deterministic catalog source data
```

Dependencies point inward: HTTP handlers depend on domain services; domain services depend on repository interfaces; the PostgreSQL package implements those interfaces. Local HTTP and Lambda entry points share the same explicit construction package, so changing the hosting model does not fork domain behavior.

### PostgreSQL

PostgreSQL owns all authoritative state. UUIDs are generated by PostgreSQL. Timestamps are UTC `timestamptz`. Money-like values use integers. Percentages use bounded `double precision` columns. JSONB is limited to localized catalog fields and immutable state/result snapshots whose internal structure is contract tested.

| Table | Responsibility | Important constraints |
| --- | --- | --- |
| `players` | Telegram identity and progression | UUID PK; unique `telegram_user_id BIGINT`; non-negative balances; optimistic `version` |
| `characters` | Playable catalog | UUID PK; unique slug; localized text; bounded stats; asset URLs |
| `encounters` | Enemy catalog | UUID PK; unique slug; localized text; bounded stats; active flag |
| `battles` | Current authoritative state | Player/character/encounter FKs; random seed; state JSONB; status/outcome checks; version |
| `battle_actions` | Auditable turn results | unique `(battle_id, sequence)` and `(battle_id, idempotency_key)`; expected/resulting versions |
| `idempotency_records` | Replayable HTTP responses | unique `(player_id, operation, idempotency_key)`; response status/body |
| `player_ledger` | Immutable progression deltas | unique `(player_id, resource_type, idempotency_key)`; optional unique battle/reason identity |
| `admin_audit_events` | Future admin accountability | actor, action, target, before/after metadata; no static admin API in the rebuild |

Player level is derived during reward application from accumulated experience. Energy is debited by the server when a battle starts and can never be set by the client. Rewards are zero for defeat and deterministic for victory.

## Battle consistency model

Battle state includes turn, hero/enemy health, special meters, combo counters, blocking flags, outcome, and the deterministic RNG cursor. The seed is cryptographically generated by the server. Each action consumes deterministic random values in a fixed order.

An action transaction performs:

1. Look up any completed idempotency record and replay it if present.
2. Lock the player-owned battle with `SELECT ... FOR UPDATE`.
3. Require `status = active` and `expected_version = battles.version`.
4. Validate the action against the current state.
5. Advance battle rules and calculate the enemy response.
6. Insert the action history and increment the battle version.
7. If complete, mark the battle once, insert ledger entries, and update player balances/version.
8. Store the response under the idempotency identity and commit.

The uniqueness constraints are the final duplicate defense. A failed statement rolls back the entire transaction, including completion rewards.

## Redis and asynchronous boundaries

Redis is used for atomic fixed-window per-player and per-IP rate limiting. Identifiers are hashed before they become keys. If Redis is unavailable, authoritative operations remain correct; the API records the degraded state and uses a bounded in-process limiter. PostgreSQL never delegates battle or progression truth to Redis.

SQS and EventBridge are not part of the initial runtime. A future delayed-energy Telegram notification would justify EventBridge scheduling plus an idempotent SQS consumer, bounded retries, a dead-letter queue, poison-message recording, and a documented redrive process.

## Production deployment

- A Lambda Function URL provides the stable public HTTPS endpoint without API Gateway, Route 53, ACM, or an Application Load Balancer. The application middleware remains the CORS authority.
- One arm64 `provided.al2023` Lambda version runs the existing Chi handler and reuses PostgreSQL and Redis connections across warm invocations. Requested reserved concurrency is capped at two. While a new AWS account cannot allocate it, deployment uses the account's reduced regional cap and automatically switches to the per-function cap once the regional quota permits it.
- Neon provides real PostgreSQL over TLS. Lambda uses its pooled endpoint with at most four connections per execution environment and no minimum idle connection; migrations use the direct endpoint so advisory locking and DDL run on one stable session. The schema, SQL, row locks, constraints, and transactions are unchanged from local PostgreSQL and the former RDS deployment.
- Upstash provides a TLS Redis-protocol endpoint. The existing `go-redis` Lua fixed-window limiter continues to use atomic `INCR`, `PEXPIRE`, and `PTTL` behavior. Redis holds no authoritative player or battle data.
- Standard-tier SSM SecureStrings hold the pooled database URL, direct migration URL, Redis URL, and Telegram token. The protected deployment workflow reads them once per release and injects them into an immutable Lambda version.
- GitHub Actions uses OIDC, not long-lived AWS keys. It builds a zip, updates `$LATEST`, publishes a numbered version, runs idempotent migrations and catalog seeds by direct invocation, promotes the `live` alias, verifies health/readiness, and restores the prior alias on failure.
- The final Terraform topology has no VPC, NAT Gateway, RDS, ElastiCache, API Gateway, load balancer, or container registry. Transitional flags retain the old private data tier only until the external cutover is verified.
- Neon and Upstash remain on their free plans with no paid add-ons. Exhausting a free usage allowance is treated as an availability limit, not a reason to upgrade automatically.

## Observability and data handling

Every response has an `X-Request-ID`; every error body repeats that ID. Structured logs include path, method, status, duration, and safe domain identifiers. OpenTelemetry HTTP spans cover the request boundary. Metrics cover request volume/latency/error rate, database latency/error rate, auth failures, starts/completions, conflicts, duplicate idempotency replays, and reward transaction failures. PostgreSQL instrumentation records duration and error state but deliberately excludes query text and arguments.

OTLP/HTTP export remains optional and fail-open for local or future collectors. The Free Plan Lambda deployment leaves it disabled. Lambda errors and throttles publish to one SNS topic, while application logs expire after a few days. Neon and Upstash usage limits are watched in their provider dashboards.

The API never logs the bot token, complete `initData`, authorization/development-auth values, database URLs, or sensitive player metadata. Expected authentication failures and validation errors are safe client messages; internal errors use a generic envelope.

## Availability and failure behavior

- `/healthz` proves that the process event loop is responsive.
- `/readyz` checks required startup state and PostgreSQL connectivity; Redis does not gate readiness.
- The local server retains explicit read-header, read, write, idle, and graceful-shutdown timeouts; Lambda enforces a bounded invocation timeout.
- Requests have bounded JSON bodies and reject non-JSON bodies where JSON is required.
- CORS returns headers only for configured HTTPS Mini App origins (plus explicit local origins outside production).
- PostgreSQL transactions, row locks, versions, idempotency records, and ledger constraints prioritize correctness over accepting a conflicting action.
